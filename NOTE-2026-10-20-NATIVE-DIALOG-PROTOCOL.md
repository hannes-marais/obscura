## Architecture inspection

The existing run_connection already separates renderer LocalSet/V8 and WebSocket I/O onto two OS threads (server.rs around 756). process_cdp_message queues ordinary pending events only after dispatch returns (around 2103), so adding ordinary pending opening events would deadlock: confirm cannot return until handleJavaScriptDialog, while that handler would be queued behind the blocked input command. The normal command watchdog also cannot release a blocking Rust host call by terminating V8 alone.

Repair path: introduce a connection-local, thread-safe dialog broker shared by the renderer and existing I/O thread. Install per-page host callback when the page/runtime is created; the synchronous op sends opening directly through the connection reply sender, then waits on a bounded response channel. Only Page.handleJavaScriptDialog may resolve the pending broker from the I/O thread; validate exact attached page session against the pending dialog, reject missing/duplicate choices, emit a real close event, and acknowledge the command before allowing the original continuation to proceed. Keep ordinary V8/DOM work on its existing owning thread. Connection teardown must wake pending waits; pending state must clear even if opening delivery or response fails. No new runtime/thread per dialog and no fabricated opening event after execution. Page/session routing and event subscriptions must be inspected before implementing; a connection-global pending slot without page identity would violate isolation.

A bounded host wait must align with command cancellation and existing watchdog budgets. Do not choose an arbitrary early autoaccept/dismiss timeout; termination must fail the command and retire pending state. Include a deterministic protocol test that sends click, waits for opening without waiting for the click reply, sends handle, and checks the original page result. This specifically detects a handler wrongly placed only in the blocked renderer dispatch queue.
